# Task Breakdown and Sequencing

Use this skill to convert a non-atomic outcome into executable work.

## Decision Rule

When the user names an exact broad deliverable and asks to break it down, propose a reviewable first draft of 3–7 practical children with varied estimates. Do not ask the user to supply the child titles merely because several reasonable decompositions are possible; the proposal is the review surface. Clarify only when the parent/outcome is genuinely unresolved or the target is atomic and needs user-specific internal content.

## Inspect Before Designing

- Resolve the exact parent task or intended category.
- Read the existing task and its current children before proposing new subtasks. Preserve useful existing work and avoid duplicates.
- Use notes, deadline, desired outcome, constraints, and prior conversation to determine the appropriate level of detail.

## Build the Plan

- For a broad project or deliverable such as a case study, application package, report, or launch, infer a reasonable small first draft of practical subtasks when the exact parent and outcome are known; do not ask the user to supply titles the model can responsibly propose for review.
- Prefer outcome-oriented subtasks with observable completion conditions.
- Sequence prerequisites before dependent work and identify work that can happen in parallel.
- Give practical estimates per subtask rather than one repeated placeholder value. Include review, coordination, and submission overhead when relevant.
- Do not decompose an already atomic action unless the user supplies meaningful internal steps or asks for a checklist. For an email, call, message, or similarly atomic action whose internal content depends on user-specific people or details, ask for those steps and do not invent generic children or emit a proposal yet.
- Preserve concrete user facts such as people, dates, blockers, deliverables, and required formats.
- When the requested outcome is a future activity whose timing depends on a prerequisite
  such as checking availability, reserving, or booking, create one parent outcome with
  distinct prerequisite and activity children. A quick availability check or booking is
  ordinarily a 5–10 minute task. Give the activity child the stated event date as its
  deadline, but do not schedule it when the user explicitly says they will choose the
  time after the prerequisite result.

## Output and Mutation

- For analysis, present the sequence, estimates, dependencies, and assumptions directly.
- For requested task-tree changes, construct one reviewable typed proposal using exact parent and task ids.
- When updating existing children with different estimates, use one metadata proposal with per-target updates.
- Clarify only when the intended outcome, exact parent, or a safety-critical constraint cannot be established.
